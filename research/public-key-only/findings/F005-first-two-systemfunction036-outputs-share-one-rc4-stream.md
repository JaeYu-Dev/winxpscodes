# F005 — First two observed SystemFunction036 outputs share one ADVAPI RC4 stream
Status: SP3 TRACE CONFIRMED
PK-only effect: removes an independent KSecDD/ADVAPI output root between the first two observed provider RNG consumptions.

## Empirical fact
V17 reports 4 `SystemFunction036` calls and 11 RC4 PRGA invocations. The useful PRGA calls are:

- PRGA #1: state pointer `0x0025ba84`, length 20, RC4 indices `i/j: 0/0 -> 20/108`, output matches SystemFunction036 #1.
- PRGA #9: **same state pointer `0x0025ba84`**, length 20, indices `20/108 -> 40/237`, output matches SystemFunction036 #2.

PRGA #2..#8 have length zero and correspond to initialization of the remaining first-use RC4 entries.

Therefore the first two `SystemFunction036` outputs are not generated by two independent ADVAPI RC4 keys. They consume consecutive 20-byte segments of the **same entry1 RC4 state**.

## Why the reuse occurs
F003 explains the startup transient:

1. First call starts with global rekey threshold 512.
2. Entry1 is first-use, so it is rekeyed from KSecDD.
3. During that rekey, NT detection changes the global threshold to 16384.
4. The first call can therefore emit 20 bytes immediately from entry1.
5. On the second call, entries2..0 are first-use under the already-16384 threshold. Each is rekeyed but gets a zero-byte PRGA pass.
6. The loop returns to entry1, whose cached state has already consumed 20 bytes, and emits the next 20 bytes.

## Algebra
Let `M1` be the 256-byte rekey material that keyed ADVAPI entry1, and let `L1,L2` be the respective 20-byte in/out buffers supplied to SystemFunction036 before RC4 processing.

Ignoring notation for RC4's internal post-use state, the first two outputs satisfy:

`R1 = L1 XOR KS_RC4(M1)[0:20]`

`R2 = L2 XOR KS_RC4(M1)[20:40]`.

Thus `(R1,R2)` share a single RC4-key root `M1`.

## Strong independence consequence
KSecDD rekeys #2..#8 occur between the two useful PRGA outputs, but they key other ADVAPI entries. They do **not** influence R2. Therefore kernel states/pools generated by those seven intervening rekeys are absent from the data-flow ancestry of the second output.

This is stronger than merely saying the calls are correlated: seven fresh-looking kernel transitions occur in wall-clock order but are data-flow irrelevant to the second RNG result.

## Public-key-only relevance
The first two rsaenh-side RNG consumptions (observed in V17 as the provider initialization call and the subsequent acquire-bridge call) do not require two independent KSecDD-derived output roots. Their ADVAPI keystream component is one recurrent stream.

This reduces the number of independent hidden roots in the provider state history. It does not yet yield a <2^128 private-key search because `M1` itself still depends on KSecDD persistent state/pool material and `L1,L2` provenance remains to be bounded/composed.

## Next composition target
Propagate the shared-stream relation through the rsaenh FIPS-186 state recurrence:

`R1 -> provider init transition`
`R2 -> acquire bridge transition`

and derive the effective image of the provider state after both transitions as a function of one RC4 root plus the two caller-buffer roots, rather than two independent OS-RNG outputs.
