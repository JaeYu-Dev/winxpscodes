# v0.1.4 — Early RSAENH ancestry pruning
Date: 2026-08-09

## New composed theorem
Combining the fixed RSAENH post-self-test state with the v0.1.3 ADVAPI same-stream finding yields a sharper dependency graph for the first two provider transitions.

The provider-initialization SystemFunction036 output and the subsequent CryptAcquireContext-bridge SystemFunction036 output are consecutive 20-byte segments of one ADVAPI entry1 RC4 stream keyed by a single KSecDD-derived rekey material `M1`.

Meanwhile, KSecDD rekeys #2..#8 occur between those two outputs only to initialize ADVAPI entries2..0. They do not affect the second useful output, which returns to entry1.

Therefore the RSAENH state after init + acquire bridge satisfies:

`S2 = F(M1,L1,L2,B1,B2)`

for fixed shipped implementation constants, where `L1,L2` are SystemFunction036 pre-call buffers and `B1,B2` are rsaenh caller-buffer prefixes. There is no dependency on KSecDD roots `M2..M8`.

## Public-Key-Only significance
This is an ancestry reduction rather than an entropy estimate. Seven fresh-looking kernel transitions disappear from the support calculation for the early provider state because they are chronologically present but data-flow irrelevant.

This reinforces the project rule:

`timeline events != independent hidden variables`.

Only values with a data-flow path into the first private scalar belong in the candidate-space theorem.

## Next target — stack/caller provenance
V17 raw pre-call SystemFunction buffers are strongly structured:

Call #1:
`98 19 03 68 00 00 00 00 00 00 00 68 00 ae 25 00 00 00 00 00`

Call #2:
`10 00 00 00 00 00 00 00 70 4b 25 00 40 fb 23 00 08 00 00 00`

Call #2 parses naturally as five 32-bit words:
`0x10, 0, 0x00254b70, 0x0023fb40, 0x8`.

These look like structured stale stack/frame data, not fresh cryptographic state, but **no support reduction is claimed yet**. The next machine-code task is to identify the exact previous writers of all 40 bytes (`L1,L2`) and the rsaenh XOR prefixes (`B1,B2`).

## Current strongest route
If these prehistory buffers reduce to fixed pointers/small counters/deterministic frame values, then the early RSAENH provider state becomes primarily a function of one KSecDD-derived root `M1`, not a sum of multiple independent 160-bit roots. The remaining challenge is then to reduce/bound M1 itself and later cached-entry roots actually consumed before the first Bitcoin private scalar.
