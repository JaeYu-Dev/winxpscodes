# v0.1.3 — NT threshold mutation + same-stream reuse
Date: 2026-08-09

## Summary
Direct V17 raw trace analysis resolved the v0.1.2 call-boundary ambiguity and exposed a startup transient caused by `g_dwRC4RekeyParam` changing from 512 to 16384 during the first NT rekey.

This produces a concrete shipped-SP3 correlation: the first two observed `SystemFunction036` outputs consume consecutive 20-byte segments of the **same ADVAPI entry1 RC4 stream**.

## Exact mechanism
### First SystemFunction036 call
- `g_dwRC4RekeyParam` is initially `0x200` (512).
- selector chooses first-use entry1 (`BytesUsed=0xffffffff`).
- local `RC4BytesUsed` captures the old 512 threshold.
- KSecDD gather path reaches `IsRNGWinNT()`, mutating the global threshold to `0x4000` (16384).
- post-rekey max calculation effectively sees `16384 - 512`, so the requested 20 bytes are emitted immediately.
- PRGA #1 uses entry1 and outputs 20 bytes.

### Second SystemFunction036 call
- global threshold is already 16384.
- entries2..0 are still first-use.
- each rekey pass has local `RC4BytesUsed=16384`, so max output is zero.
- seven KSecDD rekeys initialize entries2..0 while emitting no bytes.
- the loop returns to entry1, which already consumed 20 bytes in call #1.
- PRGA #9 emits the next 20 bytes from **the same entry1 state**.

V17 reports the same state pointer for PRGA #1 and #9, with RC4 indices continuing `0 -> 20 -> 40`.

## Raw circular-hash correction
The eight observed KSecDD IOCTL input blobs are not generated from one MD4 root:
- C1 uses `D1=MD4(B1)`.
- C2..C8 differ successively by the same `D2=MD4(B2)` embedded at offsets 7,14,21,28,35,42,49.

Thus C2..C8 form a one-128-bit-root family conditional on C1, while the complete C1..C8 tuple uses at most two 128-bit caller-side MD4 roots in this trace.

## New PK-only reduction
Let M1 be the KSecDD-derived material used to key ADVAPI entry1. Then:

`R1 = L1 XOR KS(M1)[0:20]`
`R2 = L2 XOR KS(M1)[20:40]`.

The seven KSecDD transitions that occur between R1 and R2 are **not ancestors of R2**. They initialize other cached entries only.

Therefore the first provider initialization and acquire-bridge RNG consumptions do not carry two independent KSecDD output roots; they share one cached RC4 root.

## Why this is more important than v0.1.2
v0.1.2's one-D-for-eight-inputs hypothesis was too strong and is superseded. v0.1.3 replaces it with a target-trace-confirmed statement about **output ancestry**, which is more relevant to Public-Key-Only composition: several fresh kernel operations can occur between two outputs while being irrelevant to the second output's dependency graph.
